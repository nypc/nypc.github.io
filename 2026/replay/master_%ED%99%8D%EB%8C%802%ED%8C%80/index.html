문제 풀이

1. 초기 전략

처음에는 단순히 "많은 땅을 먼저 먹고 상대방을 공격하면 승리할 수 있다"는 단순한 개념으로 접근하여 초기 모델을 만들었다. 하지만 이 코드는 성능이 좋지 못하였고, 기지 건설 및 군사 증원 타이밍, 기지 확장 위치 등 여러가지 요인을 고려해야 한다는 것을 깨달았다. 이후 처음부터 다시 확실한 승리 플랜을 설계한 후 코드를 백지 상태부터 다시 작성하였다.

초기 전략을 구상하기 위해 어떤 요인을 고려해야 할 지 포인트를 정리하였고, 이를 기반으로 코드를 작성하였다. 목차는 다음과 같다.

  1. 게임 전제
  2. 자원 단가
  3. 훈련
  4. 이동
  5. 전투
  6. 방어
  7. 초반전
  8. 종반전
  9. 행동 파이프라인

1. 게임 전제

  1. 매 턴 리포트로 양 측의 모든 정보 추적이 가능하다. 단, 상대방의 이동경로 및 이동으로 인한 골드 차이 데이터만 추정해서 얻어야 한다. 따라서 추정 데이터인 상대방의 이동 경로 예측이 매우 중요하다.
  2. 이 게임의 승리 조건은 HQ 파괴 또는 T200200200 기준 HQ HP 타이브레이크이다. 이를 위해선 게임 마지막에 상대 본부보다 어떻게든 체력이 많아야 한다.

2. 자원 단가

  1. 전사 훈련 비용, 기지 건설 및 업그레이드에 있어서 각 행동이 어느 시점에 실행되어야 경제적으로 이익이 되는지에 대한 정확한 모델링이 가능하다. 예를 들어 전사 111명을 뽑아서 골드 이득을 보려면 131313일, 신규 기지 확장은 노동 전사 포함 323232일이 걸린다. 즉 최대한의 경제 이익을 보도록 업그레이드 및 확장 순서를 정해야 한다. 또한, 본부 업그레이드는 군사의 체력 강화에도 직결되므로, 강화되는 전투력도 가치에 반영되어야 한다.
  2. T200200200까지의 게임이므로, 특정 시점이 지나면 확장이 경제적 이익이 되지 못하므로 컷오프가 필요하다. 이때 군사의 체력을 위한 본부 업그레이드는 별도로 진행되어야 한다.

3. 훈련

  1. 건설 → 이동 → 훈련 → 전투 → 노동 → 보급 순서대로 진행된다. 본부 방어 시 당일 훈련한 병력을 방어에 포함시킬 수 있다는 점을 고려해야 한다.
  2. 전사는 치유할 수 없으므로 전투력 계산시 전사의 체력을 고려해야 한다.
  3. 상비군을 항상 유지해야 한다. 이 상비군은 다음을 포함한다. 이 때 필요 수비병력 수를 계산하는 시뮬레이션을 설계해야 한다.
  4. 모든 아군 건물 건물을 지키기 위한 최소 필요 수비 병력
  5. 공격 예비대

4. 이동

  1. 너무 먼 거리에 이동 명령을 내리면 취소가 불가능하다(락 인). 즉 이동 명령은 끊어서 할 수록 유연하게 상황 판단이 가능하다.
  2. 이동 경로는 맵마다 정해져 있으므로, 상대방의 이동 경로를 파악한다면 빠르게 목적지를 추정할 수 있다.
  3. 초반의 기지 확장 순서는 다음과 같다.
  4. 서로 거리가 동일한 경합 기지를 먼저 확보한다.
  5. 경합 기지를 확보했다면, 근접 기지부터 확보한다.
  6. 상대방의 공격을 선제 대응하기 위한 최적의 집결지를 계산해야 한다(최전선 & 중앙).

5. 전투

  1. 거의 반드시 수비가 유리하다. 따라서 수비적으로 플레이하고, 상대방이 공격할 때 최대의 경제 이득을 내며 수비하는 것이 중요하다. 무조건 수비적으로 운영하되, 반드시 초반에 중앙을 확보하여서 경제적 우위를 내고, 이 차이로 승리를 확보한다.
  2. 아군 기지의 피는 수비 전사 총 HP가 버티기만 한다면 닳지 않는다.
  3. 공격 시에는 군사력을 집중하여 한번에 파괴하는 것이 이득이다. 이를 위해서 공성 가능 판정 시뮬레이션 설계가 중요하다.
  4. 방어가 가능할 만큼의 전사를 제외한 가용 가능한 전사들은 적절한 시기에 공성을 실시해야 한다. 과하게 수비적이면 안 된다.

7. 초반전

  1. 상대방이 언제 공격을 개시하는지 유의해야 한다. 상대방이 기지를 000~222개만 건설하고 본진에 가하는 공격에 적절히 대응해야 한다.
  2. 아군은 승리 플랜대로 경합지를 상대방보다 반드시 많이 확보해야 한다.

8. 종반전

  1. 무한 수비로 갔을 때 무승부가 나오는 현상을 막기 위해 경제적 우위를 반드시 중반에 내야 하고, 이를 이용해 상대방보다 아군 HQ 체력이 많거나 HQ를 파괴한다.

9. 행동 파이프라인

  1. 상태 갱신 (맵 기반 데이터 추정)
  2. 위협 분석 (상대방 경로 추정 기반)
  3. 기회 분석 (아군 공격 가능 여부)
  4. 전략 상태 (확장/압박/방어/경제 타격/종반)
  5. 예산 (생존 방어 > 노동 전사 > 확장 > HQ 업글 > 공격용 훈련 > 수리, 식비)
  6. 할당 (체력 적은 병사는 노동병으로)
  7. WA 검증

2. 팀원 간 역할 분배

처음 팀을 구성하고 나서 연습 문제인 버섯 게임에 대한 코딩을 진행해 보았다. 이 과정에서 각자의 모델을 서로 시뮬레이션하는 툴을 만들어 성능 비교를 하면 좋을 것 같다고 dltjwns119가 제안했고, 좋은 아이디어라 생각하여 이 시스템을 테스트하였다. 실제로 많은 로그 데이터를 확보하여 디버깅에도 용이하고 기능 구현에 있어서 어떤 접근법이 좋은지 판단하기 유리하여, 예선 때에도 동일하게 적용하였다. 이러한 시뮬레이션 툴을 253이 개발하였고, 이로 얻은 로그 및 대회 중간평가로 획득한 로그에 대한 분석은 MinChoi가 담당하여 이를 정리한 사이트를 만들었다. 코드의 전체적인 개발 및 검수는 이전에 언급하였듯이 초반에 각자의 접근법으로 개발을 시도하였고, hazzzelnut의 코드의 성능이 좋음을 확인한 시점부터 hazzzelnut의 코드 기준으로 버그 및 기능 개선을 하는 방향으로 작업이 이루어졌다.

3. 코드 작성 과정

사용한 LLM은 Claude Opus 4.8, GPT 5.5, Gemini Pro 3.1이 있다. 각자의 코드 개발 방식은 다음과 같았다.

  1. hazzzelnut: vscode 에디터 내부에서 Claude Code, Codex 확장 프로그램을 사용, 작업 환경 내에서 기초적인 게임 규칙 및 프로젝트의 방향성을 적은 Markdown 문서를 작성 후 코드를 개발하였다. 각 패치를 적용할 때마다 패치전 버전 기준 로그를 이용해 현재 버전으로 같은 로그를 재현하는 Replay 툴을 Gemini를 통해 생성해 이를 활용하여, 패치 내용이 의도한 시점에서 이전 버전과 다르게 로그가 분기하는지 확인하여 적용하였다. 이는 패배 후 로그 분석에 있어서도 동일하게 적용하였다.
  2. MinChoi: Claude Opus를 활용하여 중간평가 대시보드를 제작했고, 프로토타입 봇들을 제작할 때는 Codex에게 규칙과 맥락을 넣어주고 코드를 작성하였다.그리고 중간평가 대시보드를 Codex에게 넘겨주어 로그를 직접 읽어올 수 있게 하였다. 이후에는 그리고 직접 로그를 읽고 이상한 움직임을 보이는 부분을 파악해서 Codex에게 물어보고 어느 부분을 수정해야하는지 찾아내서 구현 보조로 Codex를 활용하였다.
  3. 253: 기본 작업은 vscode로 하였고 전체적인 작전 수정 시에는 Claude Code Copilot을 주로 사용하여 작업했다. 코드 부분부분 수정이 필요할 때는 Gemini Pro도 겸하여 작업했다. 코드를 작성하고 이전 모델들과 내전을 붙여보며 승률을 비교했고 로그 파일을 만들어 수정한 코드가 제대로 적용되고 있는지 확인했다.
  4. dltjwns119: 초반 클래스 구조를 기반으로 각각의 전략에 대한 Manager 인터페이스를 작성하였으며 이에 대한 전략이나 설계에 필요한 수식을 직접 설계하여 LLM (GPT 5.5)를 이용해 프롬프트를 다듬고 Codex를 이용하여 코드를 갱신하였다.

4. 발견한 문제 및 해결 과정

초기 전략을 어느 정도 구현하기 전에는 이러한 시행착오들이 있었다.

  1. 거점 확장을 느리게 하는 문제 - 골드가 충분히 있는데 이동 시간을 고려하지 않았다. 골드 모델링(예약금) 문제를 수정하였다.
  2. 상대방 HQ에 열세인 공격을 하는 문제 - 적 HQ를 공격하는 게이트에 시간, 교환비가 정확하지 않았고, 이를 수정하였다.
  3. 아군 집결지 설정 문제 - 상대방 공격에 최대한 빠르게 대응할 수 있는 최적의 집결지는 무엇인가? 에 대한 답을 찾지 못했다. 초기에 모든 아군 기지에 가장 빠르게 도달할 수 있는 중간 지점을 집결지로 설정하였으나, 이는 상대방의 빠른 공격에 대응이 매우 불리하였고, 따라서 아군 전방 기지라는 조건을 추가하였다.
  4. 상대방이 공격을 시도하는걸 예측하면 항상 기지를 포기하고 후퇴하는 문제 - 방어 조건에 아군 증원 병력이 카운팅 안되는 버그가 있었고, 이를 수정하였다.

전략이 완벽히 구현되었다 생각한 버전 7.9를 작성하여 중간평가를 치뤘고, 111111등이라는 성적을 거두어 좋아하였으나, 로그 분석후 치명적인 결함들이 파악되어 수정해야 했다. 각각의 버전에서 수정한 이전 버전의 문제점들은 다음과 같다.

  1. 8.0 - 이동 명령을 분할하는 방식이 동작하지만, 이 과정에서 최종 도착지에 기지를 지어야 하는데 중간에 돈이 충분하다면 중간 경로에 기지를 먼저 지어버리는 비일관적인 행동이 관측되었다. 이를 막기 위해서 정착 의도가 있어서 이동한 것과 중간 이동을 분리하였고, 정착 의도일 때만 기지를 건설하도록 변경하였다.
  2. 8.1 - 초반의 기지 확장 경합에 있어서, 아군이 우위를 점할 수 있는가에 대해서 항상 서로의 본부 거리를 기준으로 하였다. 하지만 이때 기지를 지을 때 아군 노동병을 보내고 기존 기지에 새로 생산된 본부 병력을 보내면 더 빠르게 확장할 수 있음을 깨닫고, 이를 적용하였다.
  3. ~8.3 - 하나의 기지를 타격한 후, 바로 재공격을 할 때 확실히 아군이 이기는 전투인지 판단을 하지 않고 재공격을 하는 버그(특히 상대 HQ에 대해)가 있었는데, HQ 연계 재목표 게이트가 문제임을 확인하였고 이를 제거하였다. 부족한 공격성은 공격/수비 판단 simulation_siege() 함수에 위임하였다.
  4. 8.4 - 아군의 기지를 방어할 때, 다른 기지에서 지원을 과도하게 하는 것이 파악되었다. 이 때 과도함이란, 555명이 공격당하는 기지에 101010명이 지원나가는 등의 과도함이었다. 따라서 방어가 가능한 최소의 수를 파견하는 것을 적용하였다. 이러한 동작의 의도는, 방어를 오래 지속할 수록 아군 포탑의 데미지로 인해 최대의 이익을 낼 수 있기 때문이다.
  5. 8.5 - 아군의 대군이 이동하는데 골드가 부족하여, 병사들이 조금씩 움직이다가 각개격파당하는 움직임이 포착되었고, 이 이동 경로에 들어가는 예산을 고려하여 순차 발진을 완화하였다.
  6. 8.6 - 상대 및 아군 HQ의 가치를 거의 무한(e18)로 설정하였는데, 이 가치를 공/수 simulation에 int에 사용하여 정수 오버플로우가 발생, 이를 train_cap으로 클램프 후 캐스팅하도록 수정하여 해결하였다.
  7. 8.7 - 집결지 방어 위치가 여전히 후방임을 확인하여, 상대방의 위협이 도달하는 날짜를 고려하여 아군의 집결지가 상대방을 항상 대응하도록(전방으로 저절로 이동하도록) 변경하였다.
  8. 8.8 - 아군 HQ에 병력이 지나치게 많이 모이고, 집결지로 이동하지 않는 문제가 관측되었다. HQ와 기지에 커밋되는 병력 알고리즘이 다른 것을 깨닫고, 이를 통일된 알고리즘으로 재설계하였다.

AI가 정작 크리티컬한 부분은 못 고치고 종속된 함수 일부만 건드리는 식이라, decide 구조 자체를 함수로 분리해 컨텍스트를 다시 잡아보려 했다. 뜯어보다 놓친 디테일도 있었지만, 코드 전체를 다시 읽고 정리하는 과정에서 가장 많이 배운 것 같다.

저는 사실 컴공이지만 PS2를 그다지 즐겨오지는 않았습니다. 하지만 알고리즘 교과목 수업만 들어본 저도, 이번 대회에 참여하게 된 건, Codex/LLM과 함께하면 내가 익숙하지 않은 도메인에서 어느 정도의 퍼포먼스를 발휘할 수 있을까를 테스트하고 싶어서였습니다.

사실 저는 대회 초반부에는 LLM에 전적으로 의존하면 좋은 봇을 만들어낼 수 있을 거라고 생각했습니다. 그래서 문제 규칙도 제가 이해하려고 하지 않았고, LLM에게 맥락만을 제공해주면서 봇을 만들어나갔습니다. 하지만 대회가 진행될 수록 이 방식에는 한계가 있다는 것을 느꼈습니다. 아무리 로그를 주더라도 LLM이 분석에는 한계가 있었고, 강력한 봇이 만들어지지 않았습니다.

그런데 이때 팀원들은 로그를 직접 읽고, 어떻게 움직이는지 관찰해서 이상한 움직임을 감지하고, 상수 임계값에 대한 한계 등 여러 문제점과 개선 아이디어를 제시했고 이 피드백들을 적용했을 때 정말로 봇의 퍼포먼스가 올라가는 걸 확인하게 되었습니다. LLM에게 로그 분석을 시켰을 때는 얻을 수 없었던 성과였습니다. 그래서 게임 도메인에 대한 이해와 집요한 로그 분석이 중요하다는 걸 팀원들 덕분에 배우게 되었습니다. 저 혼자 나갔더라면 분명히 느낄 수 없었을 것이기 때문에 팀원들에게 특히 더 감사함을 느낍니다.

개인적으로 뿌듯했던 점은 LLM을 활용해서 많은 후보를 빠르게 만들어 보고, 팀원이 낸 아이디어를 빠르게 실험해본 것입니다. 물론 초반에는 직접 로그 분석을 행하지 않아서, 실질적으로 부족함이 많았지만 그럼에도 다양한 봇을 빠르게 실험해봤다는 점에서 의의가 있다고 생각합니다. 또 중간평가 로그를 모으고 분석해 주는 대시보드를 만들어서 팀원들과 공유했고 팀원은 벤치마크를 돌리는 프로그램을 만들었는데 이런 도구들을 우리 팀 내에서 만들어서 우리의 판단과 전략을 보조하기 위해서 사용한 점이 굉장히 뿌듯했습니다.

아쉬웠던 건 문제 규칙과, 도메인 이해를 너무 늦게 시작한 게 아쉽습니다. 처음부터 로그를 읽고, 코드를 살피며 봇을 발전시켜 봤다면 더 좋았을 것 같습니다. 그리고 더 다양한 전략을 구사하는 봇을 만들어서 상성별 토너먼트를 돌렸으면 더 괜찮았겠다는 생각도 들었습니다. 팀원이 만들어낸 벤치마크 프로그램을 돌릴 때, 기존의 봇들로만 돌리니 실제 중간평가 환경과는 달라서 객관적으로 봇이 발전됐는지 확인할 수 없었던데 돌아보니 아쉽습니다. 또한 막판에는 시간과 기회가 부족하니 실험을 초기에 더 많이 해보고 종반에는 검증, 리스크 관리에 집중했어야 하는데 온전히 그러지 못한 것 같아서 아쉽습니다.

그래도 이 대회에 출전하게 되어서 저 개인으로서 성장하게 된 점이 많아서 보람을 느낍니다. 이번 대회에서 가장 크게 배운 점은 결국 도메인을 이해해야 그 도메인의 문제를 풀 수 있다는 점입니다. 그냥 전적으로 LLM에게 맡기는 건 한계가 있고, 도메인 이해를 바탕으로 LLM과 정말 끈질기게 루프를 돌아야 비로소 강력한 봇을 만들어낼 수 있다는 것, AI를 어떻게 활용해야 할지에 대한 한가지 방향성을 배운 것 같습니다.
