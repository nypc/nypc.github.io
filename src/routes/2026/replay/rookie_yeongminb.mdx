# 1. 7월 11일 11시[^kst] ~ 7월 12일 1시

**대회 규정과 지문 정독.**

문제 이해를 위한 스텝 업 문제 시도.

11:58 ~ 12:23까지 1번 ~ 5번까지 해결했다. 다람쥐로 $1/2$, $1/3$ 정도의 간단한 균등 분배 하는 것를 익혔고 행수를 늘리는 것이 이런 작은 케이스에선 좋지 않다는 것과, 경로 길이가 $\mathrm{cost}$에 중요하다는 사실 정도를 알게 되었다.

17:10 ~ 00:50까지 6 ~ 13번까지 해결했다. 좀 더 유의미한 관찰을 했다. 동일한 배치라도 다람쥐 분배 순서에 따라 $D$가 차이날 수 있다는 것을 알게 되었고 (예를 들어 6번 경우에는 $300$이 $3$의 배수라서 해바라기로부터 나오는 마지막 씨앗이 다람쥐의 $3$번쨰 방향으로 가고 그곳의 경로가 짧도록 배치하는 게 유리함), 하나의 다람쥐로 쉽게 만들 수 있는 $1/2$, $1/3$, $1/4$ 말고 여러 다람쥐를 사용해서 $1/5$, $1/7$ 등을 쉽게 만들 수 있는 방법을 고안했다.

14번은 고안해낸 방법으로 $1/7$로 균일하게 분배할 수 있는 배치를 만들었는데 과부하 때문에 $D$가 너무 커서 $0$점을 받았다. # 2. 7월 12일 10시 ~ 7월 14일 0시

**본격적인 챌린지 준비.**

오전 10시에 챌린지를 본격적으로 시작하였다. 스텝 업에서 내가 했던 것은 적당히 분수 비율로 분해할 수 있는 구조를 찾고 잘 배치하는 것이였다. 그래서 아무 시도도 하지 않은 입장에서 처음에 대충 정수론적으로 잘 계산해서 초기해를 찾고 SA[^1] 같은 알고리즘을 돌리면 될 거라고 생각했었다.

Claude Code (Opus 4.8)을 이용해서 코드를 효율적으로 짜기 위해서 `Seed Transportation` 파일을 만들었다. 문제 지문을 `\Problem\Statement.md`로 넣었고, 스텝 업의 쉬운 예제들을 `Example`이라는 별도의 파일 안에 `\Example\input_X.txt`, `\Example\output_X.txt` 모두 넣었다. 또한 만들어야 할 코드 구조를 알려주기 위해 `sample_code.c`를 넣어 놨다. 그 후 Claude Code가 분석한 문제의 구조, 문제 해결을 위한 생각과 아이디어를 물어보기 위해 프롬프트를 입력하였다.

초기 구성해를 고전적인 방법으로 만들고 SA를 이용한다는 것은 나의 생각과 동일했는데 초기 구성해를 구성하는 방법이 잘 이해가 안 됐다. 문제를 잘 이해를 못하고 한 말인 거 같기도 해서 내가 앞에서 얻은 정보들을 모두 주고 다시 계획을 제대로 세우라고 했다. 이후에 말한 초기 구성해 방식이 달라지진 않았고, SA 없이 구조적인 접근으로 풀 수 있다고 했다. 그 때 당시에는 문제에 대해 나 스스로도 문제를 잘 이해하지 못했어서 일단은 구현에 맡겼다. 구현 순서는 크게 검증기 구축, 알고리즘 순으로 진행되었다. 구현 중간 중간에 계속 확인을 했는데 아무리 생각해도 SA 없이 구조적인 접근만으로 좋은 해를 얻을 수 있을 것 같지 않았고 실제로 Claude Code가 내가 준 Example 을 테스트 해보면서 결과를 보여주었는데 결과가 좋지 않았다. 그래서 SA를 다시 제안하였고, 다시 처음에 생각했던 구조적인 방법을 통한 초기 해에 SA를 통해 최적화한다는 결론을 얻었다.

구현이 완료된 후 제출을 해 보았는데 런타임 에러, 시간초과가 났고 이를 해결한 후에도 모든 케이스에서 아래로 바로 내리는 자명하고 비용이 큰 배치를 했다. 내가 준 지문 `Statement.md`가 스텝 업의 지문이라서 제한이 훨씬 작았다는 것을 알게되었고 이 사실을 정정하며 실제 제한을 고려해서 다시 짜달라고 요구했다. 하지만 다시 짠 후에도 자명한 배치 문제도 남아있었고, 다른 배치도 비용이 $200\mathrm{K}$ 스케일로 컸기 때문에 다른 방법을 시도해야겠다고 생각했다.

추가로 아직 스텝 업 미션 14, 15에서만 만점을 받지 못했는데 이 기간 동안은 이 둘이 이전과 같은 방식으로 풀리지 않을 것이라고 생각했어서 처음엔 Claude (Opus 4.8) 에게 자체 시뮬레이터를 만들고, SA를 이용해 오랫동안 배치를 찾을 것을 요구했다. 미션 14에 대해서는 $E = D = 20$인 배치를 찾아 주었고, 미션 15에 대해서는 $E = 18$, $D = 28$인 배치를 찾아 주었다. 미션 14에 대해서는 $\mathrm{cost}$가 여전히 크다고 느껴 나 스스로 배치를 고민해 보았고 지금까지 얻은 과부하, 다람쥐 방향 순서, 경로 길이 관련 지식을 다 써서 $\mathrm{cost}$를 $7$까지 줄이는데 성공했다. 또 한 가지 얻은 것은 제한이 큰 범위에 대해 바로 아이디어를 주고 코드를 짜라고 할 때보다 작은 범위에서 LLM이 사고를 하는 과정에서 하는 관찰이 더 유효하다는 것을 알게 되었다.

# 3. 7월 14일 10시 ~ 7월 15일 1시

**문제점 분석과 새로운 시작.**

이전까지 했던 것의 문제점을 생각해보았는데 첫 번째로 문제에 대한 좋은 관찰을 알려주지 않은 상태로 처음부터 LLM에게 구현 방향을 맡겨서 좋은 결과를 얻지 못한 것 같다. 두 번째는 `Example` 파일에 있는 작은 예제들을 줬었는데 그것들의 $\mathrm{cost}$를 낮추려고 하는 경향이 있었다. 큰 제한의 문제를 해결할 때는 이 Example에 영향을 받으면 안될 것이고, 오히려 이 예제들을 통해 좋은 아이디어를 구상하는 방향으로 LLM을 활용하는 것이 좋을 것이라고 생각했다. 마지막은 $D$, $E$를 계산하는 검증기가 채점 시스템과 조금 맞지 않는 부분이 있었는데 실제 복잡한 예시에 대해 $\mathrm{cost}$가 동일하게 나오는지 확인하며 구현을 하도록 지시를 해야한다고 생각했다.

새롭게 코드를 짜기 위해 `Seed Transportation ver2`라는 폴더를 만들어 이전과 같이 `Statement.md`, `Example`, `sample_code.c`를 넣었고, Claude Code (Fable 5)에게 아래의 프롬프트를 작성하였다. 프롬프트는 미션 14, 미션 15에 대해 SA를 돌리면서 얻게 된 정보와 내가 분석한 문제점을 모두 포함하도록 Claude (Opus 4.8)을 이용해 작성했다. 구현 결과 제출 했을 때 $\mathrm{cost}$가 이전($200\mathrm{K}$) 보다 상당히($30\mathrm{K}$) 줄어들었다. 중간평가 결과도 많이 나아지긴 했으나 아직 부족하다고 느꼈다.

`Seed Transportation ver2` 폴더 내부에서 Claude Code (Fable 5)를 이용해 미션 14, 15에 대한 정답을 찾으려고 했다. 미션 14는 오전에 열심히 고민해서 $\mathrm{cost}$를 $6$까지 줄이는데 성공했다. 나의 방식을 모두 알려준 뒤 SA를 돌리는 것 대신 논리적인 추론으로 해결할 것을 요구했다. 미션 14에 대해서는 나의 배치에서 개선을 하지 못했고, 미션 15에 대해서는 수의 구조를 파악해 최적해 ($\mathrm{cost} = 3$)를 찾아 주었다. 이 과정에서 얻은 이론들을 모두 물어본 뒤 정리하였다. 가장 중요했던 수확은 단순히 SA를 돌리는 것보다 "$\mathrm{rate}$ 행렬, 격자 컴파일, 위상" 구조의 훨씬 효율적인 방법을 Claude가 스스로 찾은 것이었다.

**문제점:** 전반적으로 좋은 순위를 기록했으나 $M$이 작은 상황에서 다른 범위에 비해 안좋은 순위를 기록했다. 실제 입력을 줘서 Claude Code (Fable 5)에게 물어봤을 때 이론적 하한에 비해 큰 비용이 나오는 것을 확인했다.

**해결:** 이러한 배치들을 Claude Code (Fable 5)에게 분석을 시켰는데 majorized 하지 않은 배치라는 것을 원인으로 분석했고 $E$를 낮추는 목적으로 의도적으로 어떤 칸에 과부하가 발생하게 만들어 $D$를 조금 높이는 방향의 방식의 대기-허용 회로를 추가해 해결했다.

## 중간 평가 #19

<Figure
  src="/2026/replay/rookie_yeongminb/p4_08_Im8.png"
  alt="중간평가 #19의 C, M 구간별 등수표. M이 작은 구간은 개선되었지만 다른 구간에서 낮은 등수가 나타났다"
  width="480px"
/>

**문제점:** 이전 버전에서 좋지 못했던 영역에서의 $\mathrm{cost}$가 개선되었지만 다른 영역에서 좋지 않은 등수를 기록했다.

**해결:** 먼저 중간평가에서 $M$의 범위와 $C$의 크기가 아닌 입력 데이터의 $Q_0$ ($A$, $B$ 내림차순 정렬 시 $Q_0 = \max \displaystyle \frac{\mathrm{pref}_{B_i}−\mathrm{pref}_{A_i}}{k}$)에 따라 등수가 크게 바뀌는 걸 알게 되었다. Claude Code (Fable 5)는 $l$-벡터 탐색으로 $k$ mid-band를 정밀화하는 방법을 추천했고 이를 적용하였다.

## 중간 평가 #20

<Figure
  src="/2026/replay/rookie_yeongminb/p4_09_Im9.png"
  alt="중간평가 #20의 C, M 구간별 등수표. C=6, M이 가장 작은 구간에서 71위로 지금까지 중 가장 낮은 등수가 나왔다"
  width="480px"
/>

**문제점:** $C = 6$에서 지금까지 중에서 가장 낮은 등수가 나왔다. 이 입력 영역은 이론적 하한이 $40k$보다 커서 기존에는 단순 SA를 돌렸었다. SA가 같은 입력에도 $\mathrm{cost}$가 크게 달라질 수 있어서 이 경우에는 $\mathrm{cost}$가 엄청 크게 나온 걸로 분석했다.

**해결:** 일단 제한을 $40k$에서 $60k$로 올렸다. $40k$를 결정한 시점은 대기-허용 회로가 성능이 그렇게 좋지 않아 $40k$ 이상일 때는 SA보다 성능이 안 좋았을 때인데 저번에 $l$-벡터 탐색을 적용한 후 이 영역에서도 성능이 괜찮아진 걸 확인했다. 그래서 SA, 회로 둘 중 더 $\mathrm{cost}$가 낮은 것을 채택하는 방식으로 바꾸어 SA가 운이 안 좋아서 너무 나빠지는 경우를 방지했다.

# 5. LLM 활용

1. Claude(Opus 4.8)를 대회 규정 정리와 문제 지문 정리, 스텝 업 (미션 14, 15)을 SA로 접근, Claude Code에게 넣을 프롬프트 정리에 사용했다.
2. Claude Code(Opus 4.8 + Fable 5)는 아이디어 구상, 코드 구현에 활용했다. 또 이 리플레이 문서를 작성할 때 서식과 레이아웃(본문은 다 스스로 작성했음)을 생성하는데 사용하였다.[^2]
3. 내가 직접 한 것은 스텝 업 풀이, 과부하 조건, 다람쥐 순서 같은 여러 관찰, 문제점 분석, 코드 방향 결정 등이다.
4. 대회 규정을 확인한 후 Claude Privacy 세팅에서 "Help improve our AI models" 설정을 껐다.
5. 제공자 : Claude Max (5x)

# 6. 소감

대회를 하며 알게된 중요한 사실은 의미 있는 관찰 없이 처음부터 LLM에게 문제를 맡겼을 때 좋은 결과를 얻을 수 없다는 것이었다. 추가적인 분석을 한 뒤 코드를 짜고 중간 평가에서 등수가 상당히 오른 것을 봤을 때 가장 기억에 남는다. 또 LLM에게 문제점을 주었을 때 개선안을 주는데 그걸 단순히 적용시키보다는 이것이 실용성이 있는지 확인을 하고 채택하거나 기각하는 그런 방식이 좋다는 것을 깨달았다.

문제 상으로 아직 해결하지 못한 것은 먼저 이론적 하한과 실제 비용이 차이가 있다는 것, $\mathrm{cost}$의 이론적 하한이 $60k$ 이상인 영역에서는 단순히 SA를 돌려 $\mathrm{cost}$가 크다는 것 정도이다. 작은 아쉬움으로는 스텝 업 미션 14에 대해 상당히 많이 고민했었는데 $\mathrm{cost}$를 $5$로 만들지 못한 것이다.
